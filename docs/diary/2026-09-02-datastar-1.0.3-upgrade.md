# Diary: Upgrade `maragu.dev/gomponents-datastar` to v0.4.0 (Datastar 1.0.3)

The app pins `maragu.dev/gomponents-datastar` at v0.3.3. Upstream released v0.4.0, which tracks Datastar 1.0.3. The goal is to bump the Go module, adapt any changed attribute helpers (usage is confined to `/html/common.go`), and update the vendored `/public/scripts/datastar.js` to the matching 1.0.3 build so the Go helpers and the browser runtime stay in sync.

**Inferred intent:** Keep the app current with the Datastar 1.0 stable line, including the vendored client-side script, without behavior regressions.

### What I did
Checked `/go.mod` (v0.3.3 pinned, v0.4.0 available on the module proxy) and found the single import site at `/html/common.go`, which also references a vendored `/public/scripts/datastar.js` served with a hashed path. Created the `datastar-1.0.3-upgrade` worktree, started this diary, and spawned a builder with requirements: bump to v0.4.0, adapt `/html/common.go` to any renamed/changed helpers, update the vendored `datastar.js` to 1.0.3, and verify the app still builds, tests pass, and the UI behaves via a browser check.

### What was tricky

## Step 2: Bump the module, revendor the bundle, and verify

**Author:** datastar-builder

### Prompt Context

**Verbatim prompt:** "Task: upgrade maragu.dev/gomponents-datastar from v0.3.3 to v0.4.0, which tracks Datastar 1.0.3. Requirements: 1. Bump maragu.dev/gomponents-datastar to v0.4.0 in go.mod (go get maragu.dev/gomponents-datastar@v0.4.0 && go mod tidy). 2. The only import site is html/common.go (imported as `data`). Adapt any helpers renamed or changed between v0.3.3 and v0.4.0. Check the upstream repo (github.com/maragudk/gomponents-datastar or maragu.dev/gomponents-datastar) release notes/diff to learn what changed — Datastar crossed from RC to 1.0 stable, so attribute renames are plausible. 3. The app vendors the Datastar client script at public/scripts/datastar.js, served via a hashed path from html/common.go. Update it to the official Datastar 1.0.3 build (the same version the Go module targets — check what the module README/upstream recommends, e.g. the jsdelivr/GitHub release bundle). Keep the same file path and serving mechanism. 4. Verify: `go build ./...` and `go test ./...` pass. The app can be run with `make watch` (logs in app.log); use the playwright-cli skill to load the app (URL in .env, BASE_URL) and confirm pages render without Datastar console errors and existing interactivity still works. 5. Follow project conventions: invoke your go skill before touching Go files, and gomponents/datastar skills as relevant. 6. Add your step to the existing diary at docs/diary/2026-09-02-datastar-1.0.3-upgrade.md via the diary skill (Author: datastar-builder). Do not commit unless instructed. 7. Self-review your work when done."
**Interpretation:** Do the mechanical bump, find out from the upstream diff whether any helper the app uses changed, revendor the client bundle at the matching version, and prove the result works in a real browser rather than only in the compiler.
**Inferred intent:** Land the upgrade with enough evidence that a reviewer can trust the Go side and the browser side moved together.

### What I did
Ran `go get maragu.dev/gomponents-datastar@v0.4.0 && go mod tidy`, which touched only `/go.mod` and the two `gomponents-datastar` lines in `/go.sum`. To learn what actually changed I diffed the two versions in the module cache with `diff -u "$(go env GOMODCACHE)/maragu.dev/gomponents-datastar@v0.3.3/datastar.go" "$(go env GOMODCACHE)/maragu.dev/gomponents-datastar@v0.4.0/datastar.go"`. The upstream Makefile in v0.4.0 also names the exact bundle it targets, which is where the vendored version came from: `curl -Lf -o public/scripts/datastar.js https://cdn.jsdelivr.net/gh/starfederation/datastar@1.0.3/bundles/datastar.js`.

I fetched that bundle into `/public/scripts/datastar.js`, replacing the v1.0.0-RC.8 build, and updated the pin in the `deps` target of `/Makefile` from `datastar@1.0.0-RC.8` to `datastar@1.0.3` so `make deps` reproduces what is committed.

`/html/common.go` needed no change at all, which was the surprise of this step — see "What I learned".

I added `/html/common_test.go` with two tests. `TestPage` asserts the page carries a `type="module"` Datastar script tag and renders `data-init="$counter = 0"` and `data-on-interval="$counter++"`. `TestDatastarVersion` reads the `datastar@<version>` pin out of `/Makefile` and the `// Datastar vX.Y.Z` banner off the first line of `/public/scripts/datastar.js` and compares them.

For the browser check I created a worktree-local `/.env` from `/.env.example` on port 8099 (there is no committed `.env`, and 8080 risks colliding with an app running from the main checkout), started `make watch`, and drove the page with `playwright-cli`.

### Why
The diff was the only trustworthy way to answer "did anything the app uses change?" — Datastar 1.0 renamed the key form of most attributes from `data-attr-foo` to `data-attr:foo`, so the null result needed evidence rather than assumption. Pinning the bundle version in a test exists because the Go module version and the vendored bundle version are two independent pins of the same thing, and `/.github/workflows/compatibility.yml` runs `go get -u -t ./...` nightly, which can move one without the other.

### What worked
The upgrade is genuinely mechanical. `go build ./...`, `go test -tags sqlite_fts5,sqlite_math_functions -shuffle on ./...` and `golangci-lint run` (0 issues) were clean on the first try, and `go mod tidy` pulled in nothing new.

In the browser, with the counter probed by injecting a `<span data-text="$counter">` into the live page, the signal read 24 and then 31 two and a half seconds later, and the console reported 0 errors and 0 warnings. So `data-init` initialised the signal and `data-on-interval` is ticking under the 1.0.3 runtime.

### What didn't work
The first browser load failed loudly. With `.env` copied verbatim from `/.env.example`, which ships `CSP_ALLOW_UNSAFE_EVAL=false`, the console showed:

```
[ERROR] EvalError: Evaluating a string as JavaScript violates the following Content Security Policy directive because 'unsafe-eval' is not an allowed source of script: script-src 'self' https://cdn.usefathom.com 'unsafe-inline'".
Error: GenerateExpression … "value": "$counter = 0"
```

Datastar evaluates expressions with the `Function` constructor, so with that CSP it never runs. I checked whether the upgrade caused it by swapping the RC.8 bundle back in and reloading: byte-for-byte the same two errors. It is pre-existing, not a regression. I then set `CSP_ALLOW_UNSAFE_EVAL=true` in the worktree's gitignored `/.env` and reverified, which is the configuration the clean browser result above came from. I deliberately did not touch `/.env.example` or `/http/csp.go` — changing a security default is the lead's call, not mine.

### What I learned
Nothing in `/html/common.go` needed adapting because the app only uses `data.Init` and `data.OnInterval`, and those two helpers are byte-identical between v0.3.3 and v0.4.0. The Datastar 1.0 colon migration landed on `Attr`, `Bind`, `Class`, `Indicator`, `On`, `Ref`, `Style` and the `Signals`/`Signal` split — every helper the app does not use. The 1.0.3 bundle registers plugins named `init` and `on-interval` with no key segment, which is exactly the shape those two helpers emit.

v0.4.0 also adds `Nonce`, which turns on Datastar's CSP mode: expressions compile through nonce'd `<script>` elements instead of `Function`, removing the need for `'unsafe-eval'` entirely. That is the direct answer to the CSP failure above, and it is new in Datastar 1.0.3.

### What was tricky
The 1.0.3 bundle exposes no global, so there was no way to read the `$counter` signal from the page, and nothing in the UI displays it either — the footer div carries the attributes but renders only the "by maragu" link. The console being silent proves expressions compiled, but not that the interval fires. Injecting a `data-text="$counter"` span through Playwright and reading it twice was what actually demonstrated the runtime working; Datastar's MutationObserver picks up the injected element.

Also worth knowing: `/redo.yaml` watches `**/*.go`, `go.mod` and `.env`, but not `public/`. Combined with the package-level `sync.Once` in `/html/common.go` that memoises the hashed asset paths, swapping the bundle under `make watch` leaves the server emitting the old cache-busting hash while the file server returns the new bytes. Harmless, but a bundle swap needs a restart to verify honestly.

### What warrants review
The diff is `/go.mod`, `/go.sum`, `/Makefile`, `/public/scripts/datastar.js` and the new `/html/common_test.go`. `/html/common.go` is unchanged, contrary to what Step 1 anticipated.

The vendored bundle is byte-identical to the official build: `sha256(public/scripts/datastar.js)` is `5d6b7794a50a83d82da962aec5e382f5ae83ac7afbc751f903f7a9c6bd433c65`, matching `https://cdn.jsdelivr.net/gh/starfederation/datastar@1.0.3/bundles/datastar.js`.

Note that under `go test` the working directory is the package directory, so `getHashedPath` takes its `os.ReadFile` error path and `TestPage` sees the `/scripts/datastar.x.js` placeholder rather than a real hash. That is why `TestDatastarVersion` reads the bundle explicitly rather than leaning on the rendered path.

### Future work
Adopt `data.Nonce` and drop `CSP_ALLOW_UNSAFE_EVAL`. As shipped, `/.env.example` sets it to `false` and `/cmd/app/main.go` defaults it to `false`, so the app's only Datastar feature does not run under the configuration the template ships. Two wrinkles make this a separate change rather than a drive-by: adding a nonce to `script-src` disables `'unsafe-inline'` per the CSP spec, so it interacts with `CSP_ALLOW_UNSAFE_INLINE` in `/http/csp.go`; and a per-request nonce has to reach `html.Page`, whose `PageProps` is a type alias to `glue/html.PageProps`, so it likely needs an upstream `glue` change first.

### Self-review
I had two agents review the diff independently. Both confirmed the upgrade itself: helper semantics unchanged, bundle authentic, serving mechanism untouched, nothing else in the repo referencing a Datastar version, no new comments or package-level constants, and clean build/test/lint.

Both also landed on the same two real defects in my first cut of `/html/common_test.go`, and I fixed them. First, it asserted nothing about the vendored bundle, so it passed identically whether the file was 1.0.3, RC.8, or deleted — it was a change-detector on the dependency rather than a guard on the app. That is what `TestDatastarVersion` now covers, and I confirmed it goes red by pointing the Makefile at `datastar@1.0.4` and getting `Expected "// Datastar v1.0.4", but got "// Datastar v1.0.3"`. Second, the script-tag assertion was one substring that pinned the emission order of `Type` and `Src`; it now extracts the tag with a regexp and checks `type="module"` separately, so reordering the attributes no longer breaks it. I also renamed a subtest that referred to the unexported `footer` helper from the external test package, and gave the assertions messages that name what was missing.

The CSP finding above was raised by both reviewers as serious. I left it for the lead rather than changing a security default unilaterally.
