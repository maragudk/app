## Step 2: Bump `maragu.dev/glue` and adapt to the new `email.SendOptions` API

**Author:** glue-builder

### Prompt Context

**Verbatim prompt:** bump the dependency maragu.dev/glue to today's latest main and fix the breaking changes, then open a PR. Requirements: (1) invoke the go skill before touching Go code, and the gomponents skill if view code needs changes; (2) run `go get maragu.dev/glue@main && go mod tidy`, confirming the resolved version is from today; (3) build and test, fixing all compile errors and test failures caused by the glue update, reading the glue source rather than guessing at new APIs; (4) keep the changes minimal and mechanical, no opportunistic refactoring; (5) update this diary with my own step; (6) self-review with the code-review skill; (7) commit with the git skill conventions, push, and open a PR; (8) no telemetry work is needed unless the glue API change forces it.

**Interpretation:** Absorb one dependency bump and the smallest set of app changes that makes the app compile and pass tests against it, then ship it as a PR.

**Inferred intent:** Keep the app tracking glue's main closely with a diff a reviewer can read in a minute, rather than a bump entangled with unrelated cleanup.

### What I did
`go get maragu.dev/glue@main` resolved to `v0.0.0-20260824085602-5e40bf3e8a1d`, whose timestamp is 2026-08-24 08:56:02 — today, as expected. It pulled OpenTelemetry from 1.44.0 to 1.45.0, `go-logr` to 1.4.4, and `golang.org/x/sys` to 0.47.0 as transitive upgrades.

Exactly one thing broke:

```
jobs/register.go:23:66: cannot use opts.Sender (variable of type *postmark.Sender) as emailSender value in argument to SendEmail: *postmark.Sender does not implement emailSender (wrong type for method SendTransactional)
	have SendTransactional(context.Context, email.SendOptions) error
	want SendTransactional(context.Context, string, "app/model".EmailAddress, string, string, string, "app/model".Keywords) error
```

Glue collapsed `SendTransactional`'s six positional parameters into a new `email.SendOptions` struct, which also adds `ReplyTo` and `ReplyToName` fields the old signature had no room for. I read both the old and new `email/postmark/postmark.go` in the module cache rather than inferring the mapping, then changed `/jobs/email.go` in two places: the private `emailSender` interface now declares the new signature, and `sendLoginEmail` builds a `SendOptions` literal. Two lines of real change.

Before making it compile I wrote `/jobs/email_test.go`, which did not exist. It failed to build first (red), then passed once the mapping was in place.

I verified the rest of the bump was a no-op for the app by diffing every changed glue file against the packages the app imports. The only removed exported identifier is `gluehttp.GetRootSpanFromContext`, which the app never called.

### Why
Field mapping is where this kind of change goes wrong. Under the old positional signature the compiler caught a swapped argument whenever the types differed; under a struct literal, `Subject`, `Preheader`, `Template`, `ToName`, and `ReplyToName` are all `string`, so a swap among them compiles and ships. The test pins each of those to a distinct value, which is the only thing standing between a future edit and a login email with the preheader in the subject line.

I left `ReplyTo` and `ReplyToName` unset deliberately. Old glue always sent the sender's configured `ReplyToEmailAddress`; new glue falls back to it only when `opts.ReplyTo` is empty, so leaving both zero reproduces the old behaviour exactly. A subtest asserts they stay empty, because setting `ReplyToName` without `ReplyTo` makes new glue panic in `mustHaveAddress`.

### What worked
Reading the two versions of the glue source side by side, rather than reasoning from the compiler error alone, settled the mapping and the reply-to fallback in one pass. Diffing the exported identifiers across the whole module — `diff -ur --exclude='*_test.go'` piped through a grep for declaration lines — turned "did I miss another breaking change?" into a short list I could check by hand.

A one-line mutation of the expected panic message confirmed the new panic subtest actually fails when it should, rather than passing vacuously.

### What didn't work
`make test` could not bring up its own dependency:

```
Error response from daemon: failed to set up container networking: driver failed programming external connectivity on endpoint glue-bump-versitygw-test-1: Bind for 0.0.0.0:7072 failed: port is already allocated
```

The `versitygw-test` container from the main worktree already held port 7072. Since the compose project is named after the directory, the worktree tried to start a second one. I tore down the half-created project with `docker compose down versitygw-test` and ran the test command directly against the container already listening on 7072.

### What I learned
Glue's postmark sender now copies the keywords map before adding `appName`, `baseURL`, and `name` to it. The old one wrote those into the caller's map, so `jd.Keywords` was being quietly polluted — and a nil `Keywords` would have panicked on the write. That is a free improvement for the app, needing no change here.

New glue also panics on an empty recipient (`no recipient email address given`) where the old one would have sent a malformed address and taken an API error back. `jd.Email` is unvalidated job data, but goqite's runner recovers panics, so either way the job fails and retries.

### What was tricky
Deciding what *not* to fix. Both reviewers independently found a real telemetry regression this bump introduces, outside the file I touched — see below. It is caused by the bump, but no glue API forces the change, and the brief scoped telemetry work out. I left it out of this PR and raised it instead of quietly widening the diff.

### What warrants review
`/http/auth.go` is the thing to look at, and it is *not* in this diff. Glue removed the child spans from `Authenticate`, `Authorize`, and `SavePermissionsInContext` this bump, and `TracingMux` lost its tracer: instead of opening an `http.Handler` span, `wrapHandlerFunc` now records `handler.duration_ms` onto whatever span the request context carries, which is meant to be the main server span. The app's `AddUserToContext` still starts a child span and puts it on the request, and it is registered after glue's `OpenTelemetry` middleware and before the routed handler. So `handler.duration_ms` — and any attribute an app handler sets through `trace.SpanFromContext` — now lands on the `AddUserToContext` child span instead of the main span, invisible to queries filtering on `main = true`. Glue documents this exact caveat on `setSpanDuration`: "Anything which starts a span in between takes the attribute with it."

The fix mirrors what glue did to its own three middlewares: delete the tracer and the span from `AddUserToContext` and keep only the `context.WithValue`. It is a four-line deletion, but it is telemetry work the brief excluded, so it needs a decision rather than a guess.

Otherwise: check the six field assignments in `sendLoginEmail` against the old call site, and confirm leaving reply-to empty is the intent.
