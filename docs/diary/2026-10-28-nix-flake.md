# Diary: Experimental Nix flake

Goal: try building the app with Nix. Add a `flake.nix` with a package and a dev shell, verify it in a repo-local GitHub Actions workflow on a draft PR, and do not merge. The Dockerfile, Makefile and existing CI stay as they are.

## Step 1: Requirements and delegation

**Author:** main (lead)

### Prompt Context

**Verbatim prompt:** Could we try building this app with nix instead?

**Interpretation:** Explore Nix as a build tool for the app. Through a short brainstorm, Markus scoped it to: (1) a flake with `packages.default` and `devShells.default` only, no Nix-built image, Dockerfile/Makefile/CI untouched; (2) no local Nix install, verify in GitHub Actions instead; (3) don't merge, keep it on an experiment branch. He then said "Skip the sections, just try building it and make a PR".

**Inferred intent:** Find out whether Nix is a pleasant, working way to build this app, with zero risk to the current build and deploy path and nothing installed on the Mac Mini.

### What I did
Surveyed the build: multi-stage `/Dockerfile` (curl'd Tailwind CLI for CSS, CGO `go build -tags sqlite_fts5,sqlite_math_functions ./cmd/app`, `debian:trixie-slim` runner with `public/` and `sqlite/migrations/`), CI/CD via shared `maragudk/workflows`, Go 1.27, `mattn/go-sqlite3` (CGO). The app reads `public/...` relative to its working directory (`/html/common.go`).

Markus tried the official Nix installer (`curl -L https://nixos.org/nix/install | sh`) on the Mac Mini (macOS 27.0.1). It failed at the volume step with `vifs: error creating /etc/fstab`, leaving `/etc/synthetic.conf`, an empty APFS volume "Nix Store" (`disk3s7`) and an empty `/nix` mount point. No build users, LaunchDaemons, keychain entry or shell rc edits had been made. Markus removed the volume (`sudo diskutil apfs deleteVolume disk3s7`) and `/etc/synthetic.conf`; I verified both were gone. `/nix` disappears on the next reboot. That led to the decision to verify in CI only.

Created worktree `nix-flake`, started this diary, and spawned one builder.

### Why
A flake with package + dev shell is the idiomatic Nix setup and the smallest thing that answers "does Nix work for this app". A Nix-built image would mean replacing the Dockerfile and changing CD, and building Linux images on macOS needs a Linux builder, so it is deferred.

### What worked
N/A yet.

### What didn't work
The official Nix installer on macOS 27.0.1 failed: `vifs: error creating /etc/fstab` after creating the APFS volume. No known upstream report found for this exact error.

### What I learned
On macOS, Nix is a system install, not a CLI: an APFS volume mounted at `/nix` via `synthetic.conf` and `fstab`, 32 `_nixbld` build users, a root `nix-daemon` LaunchDaemon, and edits to `/etc/zshrc` and `/etc/bashrc`. Worth stating up front next time.

### What was tricky
`buildGoModule` pins a `vendorHash`, so any `go.mod`/`go.sum` change breaks `nix build` until the hash is updated. That maintenance cost is the main argument against merging the flake without a permanent CI check.

### What warrants review
Whether the flake output layout matches the Docker runner layout, and whether the CI workflow only runs on this branch and leaves the shared workflows alone.

### Future work
If the experiment is kept: decide on a permanent CI check, a Nix-built image (`dockerTools.buildLayeredImage`), and Makefile integration with the dev shell.

## Step 2: Build the flake and verify it in GitHub Actions

**Author:** fabrik:builder

### Prompt Context

**Verbatim prompt:** You're building an experimental Nix flake for this Go web app, in the worktree /Users/maragubot/Developer/app/.claude/worktrees/nix-flake (branch `worktree-nix-flake`). [...] Requirements: 1. `/flake.nix` + `/flake.lock` at the repo root. [...] 2. `/.github/workflows/nix.yml` [...] 3. Do not change /Dockerfile, /Makefile, or the existing workflows. No Go code changes. 4. Open a **draft** PR against `main` (push the branch as `nix-flake`). [...]

Mid-run, the lead added: "New option from Markus: you can run Nix locally inside Docker (daemon is running, aarch64 linux) instead of iterating only through CI. [...] This covers aarch64-linux only, so the GitHub Actions workflow is still required [...] Clean up any Docker volume you create when you're done, and note the Docker approach in the diary."

**Interpretation:** Write `/flake.nix` (package and dev shell on nixos stable with Go 1.27). Get `/flake.lock` and the real `vendorHash` without a local Nix install. Add `/.github/workflows/nix.yml` to check the build, the layout, the dev shell and a smoke run on three systems. Open a draft PR.

**Inferred intent:** Find out cheaply, without touching the real build path, whether Nix builds this app cleanly on Linux and macOS, and what keeping it would cost.

### What I did
Checked nixpkgs through the GitHub API instead of with Nix. `nixos-26.05` is the newest stable branch. Its `pkgs/top-level/all-packages.nix` has `go_1_27` (from `1.27.nix`, version 1.27.3) and `buildGo127Module`, though the default `go` is still `go_1_26`. `tailwindcss_4` is 4.3.1, packaged as the upstream standalone binary (`fetchurl` from the GitHub release, `autoPatchelfHook` on Linux). So no fallback to unstable was needed. `/public/scripts/datastar.js` is committed in git, so the build doesn't need `make deps`.

Wrote `/flake.nix` with a plain `forAllSystems` over `nixpkgs.lib.genAttrs`:
- `packages.default` is `buildGo127Module` with `subPackages = [ "cmd/app" ]`, the two sqlite tags, `env.CGO_ENABLED = 1`, `doCheck = false`, and a `postInstall` that copies `public/` and `sqlite/migrations/` into `$out` and runs `tailwindcss --minify` into `$out/public/styles/app.css`.
- `devShells.default` is `mkShell` with `go_1_27`, `tailwindcss_4`, `golangci-lint` (overridden, see below), `gotools` and `sqlite`.

Wrote `/.github/workflows/nix.yml`: matrix `ubuntu-latest`, `ubuntu-24.04-arm`, `macos-latest`, with `cachix/install-nix-action@v31.11.2` (v31.11.3 was one day old, so I took the previous release). It checks that `builtins.currentSystem` matches the matrix entry, then runs `nix flake check --no-update-lock-file` and `nix build`. It checks the output layout and the dev shell (Go version, tools on `PATH`, `golangci-lint` version, a CGO `go build`, `golangci-lint run`). Then it smoke-tests the binary and checks that the app's migrations ran.

Bootstrapped the two hashes in CI. The first push had no `flake.lock`, `vendorHash = lib.fakeHash`, and a temporary step that printed `flake.lock`. Nix wrote the lock on the runner, and the build failed with the real hash. I copied the lock from the log (identical on all three runners) and the hash into the flake, and removed the print step.

Opened draft PR #77 from `nix-flake`, with Markus as reviewer. After the code review (Step 3), and once Markus allowed it, I re-verified everything locally on aarch64-linux in Docker.

### Why
The output layout mirrors the Docker runner (`bin/app`, `public/`, `sqlite/migrations/`). The app reads `public/...` and `sqlite/migrations` relative to its working directory, so you run it from `result/`, like Docker runs it from `/app`. The smoke test only needs SQLite, because the S3 bucket and Postmark sender make no network calls at startup. That's why I could add it without external services.

### What worked
- `nixos-26.05` has everything: Go 1.27.3, Tailwind 4.3.1, sqlite 3.51.2, gotools 0.44.0.
- CGO and `mattn/go-sqlite3` built on darwin with no extra inputs; the stdenv clang just works.
- Tailwind v4's standalone binary ran fine in the Linux sandbox (no `HOME` or network trouble) and on darwin. `app.css` came out at 8704 bytes with the same content hash (`/styles/app.4c07c446...css`) on all three systems and in Docker.
- `vendorHash` is the same on all three systems: `sha256-weqxOti+puOgddzr06a5VG/Pl3yL22st2rBtcsWH+vU=`.
- Smoke test: the binary starts from `result/` with `DATABASE_PATH=$RUNNER_TEMP/app.db`. It serves `/` with a hashed CSS path, which proves it found `public/styles/app.css`, and it serves that CSS. Afterwards the DB has the app's tables (`users`, `sessions`, `accounts`, ...).
- Final Nix run 40707815422 is green on all three runners (4m17s aarch64-linux, 5m1s x86_64-linux, 6m32s aarch64-darwin). The existing CI and Security workflows are green on the PR.
- Running the checks locally in Docker: `docker run --rm -v app-nix-flake-store:/nix -v <worktree>:/src:ro -v <scratchpad>/docker:/scripts:ro nixos/nix:latest /scripts/check.sh`. The script sets `NIX_CONFIG="extra-experimental-features = nix-command flakes"`, uses the flake ref `path:/src`, and builds into `/tmp/result` so the read-only worktree mount stays untouched. Docker seeds the named volume from the image on first use, and it keeps the store between runs. The image has Nix 2.35.4. A cold run took about two minutes.

### What didn't work
- The first CI run failed the build, as planned: `error: hash mismatch in fixed-output derivation '/nix/store/06xyffn2ki3v8sjqhxs9qqfys8wvpkj8-app-d7e7971-dirty-go-modules.drv': specified: sha256-AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA= got: sha256-weqxOti+puOgddzr06a5VG/Pl3yL22st2rBtcsWH+vU=`.
- `golangci-lint` from `nixos-26.05` (2.12.2) can't lint this module. Stock, it's built with Go 1.26, and golangci-lint refuses to lint code that targets a newer Go, so I had already overridden it to build with `buildGo127Module`. Even so, `golangci-lint run` in the dev shell failed on all three runners: `model/auth.go:4:2: could not import maragu.dev/glue/model (... could not import internal/goarch (-: could not load export data: internal error in importing "internal/goarch" (cannot decode "internal/goarch", export data version 5 is greater than maximum supported version 4); please report an issue))))) (typecheck)`. Its vendored `x/tools` predates Go 1.27's export data format. I fixed it by overriding to 2.15.0, with the same `src` hash and `vendorHash` as the `nixpkgs-unstable` package, built with `buildGo127Module`. After that it reported `0 issues.` everywhere.
- After the first `git push -u origin worktree-nix-flake:nix-flake`, a plain `git push -q` pushed nothing, and the only output was the hint to read `git help config`. The local and remote branch names differ. Use `git push origin HEAD:nix-flake`.
- The first Docker attempt failed with `exec /scripts/check.sh: permission denied`. The script needed `chmod +x`.

### What I learned
- Even on a fresh stable branch, the nixpkgs default Go lags the newest packaged Go. So anything built with plain `buildGoModule` (golangci-lint, gotools) uses Go 1.26. For linters that matters, because they load export data from the Go toolchain they run with. `gotools` also wraps `goimports` with Go 1.26 on a `--suffix PATH`, which is why `go-1.26.8` shows up in the dev shell closure. `go version` in the shell is still 1.27.3.
- `buildGoModule` is built on `lib.extendMkDerivation` and reads `finalAttrs.vendorHash`, so `overrideAttrs` can cleanly change `version`, `src` and `vendorHash`. The `ldflags` that use `finalAttrs.version` follow too: `golangci-lint version` reports 2.15.0.
- The overridden golangci-lint has the same `go-modules` FOD hash as the unstable package, so cache.nixos.org served that derivation and only the final compile ran locally.
- Inside Docker, a git worktree can't be used as a `git+file` flake. Its `.git` file points into the main repo's `.git/worktrees/`, which isn't mounted. `path:/src` works, and with the allowlisted `src` (Step 3) it's also safe.
- The Nix-built binary logs `"version":"unknown"`. The build sandbox has no `.git`, so Go stamps no `vcs.revision`, and that's what glue reads for the OTel `service.version` (see `/docs/diary/2026-08-20-otel-service-version-unknown.md`). `-X` ldflags can't fix this, because glue reads build info, not a variable.

### What was tricky
- Tailwind sources. `/tailwind.css` has `@source "/go/pkg/mod/maragu.dev/glue*/html/**/*.go";`, which is the Go module cache path inside the Docker build image. In Nix, the glue code is in `vendor/maragu.dev/glue/html`. I didn't want to change `/tailwind.css`. Instead, `postInstall` copies `tailwind.css` and `html/` into a scratch `css/` directory, like the Docker CSS stage, which only had those files. It appends `@source "../vendor/maragu.dev/glue/html";` and runs Tailwind from there, so Tailwind's automatic source detection doesn't scan the whole vendor tree. The workflow checks for `.min-w-12`, a class that only glue's pagination uses, to show that Tailwind scanned the vendored glue code.
- Producing `flake.lock` without Nix. A `narHash` is hard to compute by hand, so CI wrote the lock and I copied it out of the log. With Docker this is now one command.

### What warrants review
- `/flake.nix` `postInstall`: the Tailwind source workaround, and whether the output layout matches the Docker runner.
- `/flake.nix` `src` allowlist: a new top-level Go package directory must be added there. If one is missing, the build fails loudly.
- The `golangci-lint` override in the dev shell. It pins version, `src` hash and `vendorHash`, and depends on the nixpkgs package taking a `buildGo126Module` argument.
- To validate: look at the Nix workflow runs on #77, or run the Docker command above.

### Future work
- `vendorHash` breaks on every `go.mod`/`go.sum` change, Dependabot included. Keeping the flake would need automation that updates it, or a permanent CI check that people know how to fix.
- Nix builds report `service.version=unknown`. Fixing that needs glue to accept a version from ldflags or an env var.
- CI has no Nix binary cache, so each run rebuilds the app and golangci-lint (4 to 7 minutes per runner).
- `nix run` from another directory starts the app without `public/` or the app's migrations, and glue silently skips a missing migrations directory. A wrapper with `--chdir $out` would also need an absolute `DATABASE_PATH`, so I left it out.

## Step 3: Self-review

**Author:** fabrik:builder

### Prompt Context

**Verbatim prompt:** Self-review your diff before finishing.

**Interpretation:** Run the code-review skill over PR #77 and fix what is worth fixing for an experiment.

**Inferred intent:** Don't hand back an experiment whose conclusions rest on a misleading build.

### What I did
Ran `/code-review medium 77`, which returned nine findings. I fixed three:
- `src` used `lib.fileset.difference ./. [...]`, which relies on the flake being fetched from git. With `nix build path:.` it would copy `.env`, `app.db*` and a local `tailwindcss` binary into the store. I changed it to an explicit allowlist (`go.mod`, `go.sum`, `tailwind.css`, and the Go package and asset directories) that also leaves out a locally built `public/styles/app.css`. `lib.fileset.gitTracked` wasn't an option, because in a flake `./.` is a store path with no `.git`.
- The dev shell step printed the `golangci-lint` version without checking it. Now it greps for `version 2.15.0 built with go1.27`, so the step fails if the override is silently ignored.
- The smoke test couldn't notice skipped app migrations. I added a step that runs `sqlite3 "$RUNNER_TEMP/app.db" .tables` in the dev shell and requires `users`.

I left the other six and wrote them down in Step 2 Future work and in the PR description:
- `nix run` from another directory.
- `service.version=unknown`.
- The Tailwind `@source` workaround. A real fix changes `/tailwind.css` for all builds.
- The `vendorHash` cost on every PR.
- The override depending on the name of the `buildGo126Module` argument.
- No binary cache.

Before pushing, I re-ran everything in Docker on aarch64-linux. It passed with the same CSS hash, so the `src` change didn't change the output. Then all three CI runners passed (run 40707815422).

### Why
The allowlist and the two checks are cheap, and they make the experiment's results trustworthy. The rest are either out of scope (they need Go or `/tailwind.css` changes) or are costs of keeping the flake, which is Markus's call.

### What worked
The Docker loop turned checking the review fixes into a two-minute local run instead of a CI round trip.

### What didn't work
Nothing failed in this step.

### What I learned
`nix flake check` only checks the current system, and says so: `warning: The check omitted these incompatible systems: aarch64-darwin, x86_64-linux`. That's why the three-runner matrix matters.

### What was tricky
Telling apart the findings that matter for an experiment from the ones that only matter if the flake is kept.

### What warrants review
Whether the allowlist is the right default, or whether a denylist plus the git-fetched flake source is good enough.

### Future work
None beyond Step 2.
